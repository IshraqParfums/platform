# 03 - Database Design

**Project:** Ishraq Parfums
**Document Version:** 1.0
**Status:** Draft (Version 1 / MVP)

---

# 1. Purpose

This document defines the logical and physical data model for the Ishraq Parfums platform.

It specifies:

* Business entities
* Relationships
* Data ownership
* Lifecycle states
* Constraints
* Indexing strategy
* Data design principles

This document does not define API endpoints, business workflows, or implementation details.

---

# 2. Data Design Principles

The database design should prioritize:

* Data integrity
* Simplicity
* Maintainability
* Read performance for customer-facing pages
* Clear ownership of data
* Extensibility for future features

General principles:

* Use relational modeling.
* Prefer normalized data with selective denormalization where it improves read performance.
* Use soft deletes where applicable.
* Store files outside the database and persist only metadata.
* Track business state using explicit status fields.

# 4. Entity Responsibilities

## Customer

Stores customer identity and account information.

Responsibilities:

* Authentication identity (phone for WhatsApp OTP)
* Contact information
* Profile information

---

## Customer Address

Stores one or more delivery addresses for a customer.

Rules:

* A customer may have multiple addresses.
* One address may be marked as default.

---

## Collection

Groups products into logical collections.

Examples:

* Designer
* Nostalgia

---

## Product

Represents a ready-made perfume available for purchase.

Contains:

* Name
* Collection
* Short description
* Detailed description
* Product status (Draft / Active / Archived)

Products do not directly store stock.

Lifecycle rules:

* Draft and Active may move between each other.
* Archived is terminal for catalog purposes and cannot return to Draft or Active.

---

## Product Variant

Represents a purchasable size of a product.

Example:

* 30 ml
* 50 ml
* 100 ml

Variant stores:

* Price
* Stock quantity
* SKU (future)
* Availability

Inventory is managed at this level. There is no separate inventory table in Version 1.

---

## Product Image

Stores metadata for product images.

Supports:

* Multiple images
* Display order

Image binaries are stored externally.

---

## Bespoke Perfume

Represents a generated bespoke recommendation.

Characteristics:

* Generated by the application scoring engine
* Independent from the product catalog
* Customer may rename it
* Fixed V1 commercial offer: ₹1,000 for 100 ml
* Not inventory managed
* May be added to cart
* May be ordered

Suggested stored fields for Version 1:

* Display name (editable)
* Generated formula snapshot (JSON)
* Answer snapshot (JSON)
* Mood / explanation text
* Size (100 ml)
* Unit price (1000)
* Owning customer (null until login merge)

Guest results are not required to live in the database until authentication merges them.

---

## Cart

Represents a customer's active shopping cart.

Supports:

* Ready-made perfumes
* Bespoke perfumes
* Mixed carts

Only one active cart exists per authenticated customer.

Guest carts are client-side (local storage) and merge into this entity on login.

---

## Cart Item

Represents an individual item within a cart.

Each item references either:

* Product Variant
* Bespoke Perfume

---

## Order

Represents a completed purchase.

Contains:

* Customer
* Delivery address snapshot
* Flat shipping amount (₹50 in Version 1)
* Order total
* Order status
* Linked payment

---

## Order Item

Stores purchased products.

Supports:

* Ready-made perfumes
* Bespoke perfumes

Order items are immutable once created and should snapshot name, size, and price at purchase time.

---

## Payment

Stores Razorpay payment records linked to an order.

Typical fields:

* Provider (Razorpay)
* Provider payment / order identifiers
* Amount
* Status
* Raw verification metadata as needed

---

## Review

Stores customer reviews.

Rules:

* One review per customer per product.
* Reviews are editable.
* Reviews require authentication.
* A derived or stored **verified buyer** flag indicates whether the reviewer purchased the product.

---

## Admin User

Represents administrative users responsible for managing the platform.

Admin authentication is handled by Supabase Auth (email and password). The database stores the admin profile / linkage needed by the application.

Responsibilities:

* Product management
* Inventory management
* Order management
* Basic customer management

## Customer

* One Customer → Many Orders
* One Customer → Many Reviews
* One Customer → Many Bespoke Perfumes
* One Customer → Many Payments (through orders)

---

## Collection

* One Collection → Many Products

---

## Product

* One Product → Many Variants
* One Product → Many Images
* One Product → Many Reviews

---

## Questionnaire

* Not modeled as tables in Version 1 (application-code engine ported from the existing prototype)

---

---

## Order

* One Order → Many Order Items

# 6. Lifecycle States

## Product

* Draft — editable, not customer-visible; may become Active
* Active — live in catalog; may return to Draft
* Archived — terminal catalog state; retained for history; cannot return to Draft or Active

---

## Order

* Order Received
* Confirmed
* In Production
* Ready for Dispatch
* Dispatched
* Delivered

Version 1 does not include a Cancelled status.

---

## Payment

Suggested statuses:

* Created
* Paid
* Failed

Exact Razorpay status mapping is an implementation detail.

# 7. Data Integrity Rules

The following business rules should be enforced by the database where practical:

* Phone number must be unique (customer WhatsApp OTP identity).
* Email may be stored and should be unique when present.
* One review per customer per product.
* A variant belongs to exactly one product.
* A product belongs to exactly one collection.
* A bespoke perfume belongs to exactly one customer after authentication.
* Product variants cannot exist without a product.
* Product images cannot exist without a product.
* Archived products must not be sold as new catalog items.
* Order items snapshot commercial details at purchase time.

---

# 8. Soft Delete Strategy

Soft delete / retention approach for Version 1:

* Products use explicit status (**Archived**) rather than a separate soft-delete flag for removal from catalog.
* Reviews may support soft delete if needed later.
* Bespoke perfumes remain retained once owned by a customer.
* Orders and payments are retained as historical records.

Archived products remain available for historical order reference.

---

# 9. Indexing Strategy

Indexes should optimize common application queries.

Recommended indexes include:

* Customer phone number
* Customer email (when present)
* Product status
* Collection
* Product name
* Order status
* Review (customer_id, product_id)
* Product Variant (product_id)
* Product Image (product_id, display_order)
* Bespoke Perfume (customer_id)
* Payment provider identifiers

Composite indexes should be introduced only when justified by actual query patterns.

---

# 10. Storage Strategy

The database stores only structured data.

External storage should be used for:

* Product images
* Future media assets

Only metadata (URL, filename, display order, etc.) is stored in the database.

Guest cart and guest bespoke recommendation data may live in browser local storage until login merge; they are not required as first-class guest tables in Version 1.

---

# 11. Future Expansion

The model is designed to support future additions such as:

* Wishlist
* Coupons
* Address-based shipping rates
* Shipment tracking
* Notifications
* Questionnaire CMS tables
* Recommendation versioning
* Inventory history
* Audit logs
* Order cancellation

These features should integrate without major schema redesign.
